Task: implement the query layer — AST, the query-string DSL (parser and serialiser), the evaluator, and the
filter → sort → group pipeline that turns rows + view config into the visible row set. Pure TypeScript.

Read first: `docs/01-spec.md` §filters, §the query string, §sort, §grouping (the DSL and the operator table
are the spec, and legacy filters must keep their old meaning), `docs/02-architecture.md` §Query,
`docs/08-decisions.md` §E4 and the query decisions; the reference implementation for behaviour (not code) is
`prototype/js/query.js` — read it to see the exact behaviours, then write your own.

Deliverable:

1. `src/core/query/ast.ts` — `Expr` as a closed union: `{ kind: "and" | "or", parts }`,
   `{ kind: "not", part }`, `{ kind: "cmp", fieldId, op: FilterOpId, operand }`,
   `{ kind: "empty", fieldId }`, `{ kind: "unparsed", text }`. Plus `serialize`/`deserialize` to a plain
   JSON shape (this is what gets stored in the `.base` sidecar, so it must be stable and versioned).
2. `src/core/query/parse.ts` — `parseQueryString(text, ctx): ParseResult` where the result carries the AST
   **and** the list of errors with character offsets. Requirements:
   - everything `docs/01` specifies: quoted strings, `>`, `>=`, `<`, `<=`, `=`, `!=`, `~` (contains),
     the empty/blank operator, `and`, `or`, `not`, parentheses, numerals, booleans, dates and
     parenthesised groups;
   - an unparseable fragment does **not** throw and does not discard the rest: it becomes
     `{ kind: "unparsed", text }` and appears in the error list, so the UI can show the offending span;
   - the parser is total: for any input string it returns a result (property-style test over generated
     strings), and never loops forever.
3. `src/core/query/serialize.ts` — `toQueryString(ast, ctx): string` such that
   `parseQueryString(toQueryString(ast))` round-trips for every AST in the fixture table
   (normalisation differences are allowed and must be listed in a comment).
4. `src/core/query/evaluate.ts` — `evaluate(expr, row, ctx): boolean`, dispatching through the registry's
   `matches` (never a `switch` on type). Includes the short-circuit order and the documented behaviour for
   an operand that does not parse (`false`, plus a reason the UI can show once per field).
5. `src/core/view/pipeline.ts` — `buildView({ fields, rows, view, queryAst }): ViewResult` returning
   `{ rows, groups, hiddenFieldIds, columnOrder }`:
   - filters first, then search text (the toolbar's search box searches all visible values via
     `formatPlain`/`formatDisplay` — document which one you chose and why),
   - sorts applied in order with a stable tiebreak on the row's file path (this is what makes a 5,000-row
     grid deterministic — assert it),
   - grouping produces group keys and counts with the registry's `groupKey`, plus collapse state carried
     from the view config,
   - `ViewResult.rows` is the flat, already-ordered list the grid windows over, including group header
     pseudo-rows only if the docs say so — state your decision in a comment and in the report.
6. `tests/unit/query-table.test.ts` — the table of `(expr, row, expected)` from `docs/01` plus one row per
   filter operator per applicable type, generated by iterating the registry.
7. `tests/unit/query-legacy.test.ts` — the legacy DSL strings from the old README (read them from
   `../airtable-tabula` if it is cloned; otherwise from the fixtures you write from `docs/01`) must parse
   to an AST that matches the same rows as before. This is the test that proves the migration keeps old
   filters meaningful.
8. `tests/unit/pipeline.test.ts` — sort stability, multi-level sort with a tiebreak, grouping counts,
   collapse state, and a 5,000-row timing assertion that the pipeline itself stays under 50 ms on the
   fixture data (state the machine's numbers honestly; this is a smoke budget, not a benchmark).
9. `PROGRESS.md` updated.
